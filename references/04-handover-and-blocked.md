# 交接、blocked 与早间验收

## blocked 的三个条件

任务转 blocked 必须同时满足：
1. 已尝试 3 次（不是"我觉得不行"）；
2. 有可复现的证据（验收输出、文件行数、错误栈）；
3. 说清"需要人做什么决定"（改阈值？补数据？换方案？）。

不许的 blocked：等一会儿再试、环境有点慢、我不确定所以停下。

## 一个 blocked 不要连坐整晚

任务 B 依赖 A 时，A blocked 则 B 也标 blocked（依赖缺失），但**不相关的任务继续做**。夜间的目标是"推进尽可能多的独立任务"，不是"全线停下等批复"。

## 交接字段

每晚收工，提示词里必须给下一晚这些：

```
- 分支 / HEAD sha
- 未提交改动（文件 + 一半做到哪）
- 今晚先收尾哪个任务，为什么
- 阈值变更记录（哪天、改了什么、为什么、谁批准）
- 上一晚 blocked 的列表（含证据位置）
```

没有这些，第二晚的 agent 会从零猜，最常见的表现就是重做已完成的任务。

## 早间三问

1. 验收命令我重跑了吗？——不看它写的总结，自己跑。
2. 数字对得上吗？——PROGRESS 的行数/成功率，和产物实际行数比。
3. 留下什么决定给我？——阈值、口径、要不要继续；be 具体到"改哪个值、改成多少"。

## 时间戳纪律

**写时间之前先跑 `date`。**

凭印象写"现在 20:15"，实测连续三次写错：一次整段往后推了 10–30 分钟，一次把凌晨写成 00:45（实际 00:14），一次把下午写成 20:16（实际 19:58）。错的时间戳会让日志失去审计价值——你无法再用"日志时间 vs 提交时间"判断 agent 是否在编。

正确做法：每条 PROGRESS 落笔前跑一次 `date "+%Y-%m-%d %H:%M:%S"`；如果批量补记，按事件顺序写范围并注明"近似"。

## 收工条件

- `git status` 干净；
- 所有今晚任务的状态是 done 或 blocked，没有 doing；
- bundle 已生成并 verify；
- 报告里只有三样：HEAD、状态清单、需要人决定的事。

## 一个反直觉的观察

给 agent 的自由度越大，它越倾向于"做一些看起来像进展的事"（写文档、重构脚本、跑分析），而不是做那个可能失败的验收任务。所以夜间提示词里要写死"一次只做一个任务，做完就提交"，并且验收失败三次就停——这条纪律比任何"请认真完成"的措辞都有效。
